# Thermal Kavach API

Run migrations with `alembic upgrade head`, then start the API with `uvicorn app:app --reload`.

## Ward overview

`GET /wards`

Example response:

```json
[
  {
    "ward_id": "W-01",
    "name": "Dehgam Central",
    "vulnerability": {"elderly_pct": 13, "outdoor_worker_pct": 28, "informal_housing_pct": 22},
    "latest_weather": {"id": 7, "timestamp": "2026-09-08T10:00:00Z", "temp_c": 38.2, "humidity_pct": 48, "wind_kmh": 12, "wbgt_c": 30.4, "risk_tier": "high"},
    "latest_risk": {"tier": "high", "observed_at": "2026-09-08T10:00:00Z"}
  }
]
```

`GET /wards/W-01` returns the same ward data plus `recent_reports`, limited to the five newest reports. An unknown ward returns `404`.

## Health reports

```http
POST /health/report
Content-Type: application/json
```

```json
{"ward_id":"W-01","severity":"moderate","source":"hospital","notes":"Two heat exhaustion cases","reporter_contact":null}
```

The response is `201 Created`; `reported_at` is generated by the API. `GET /health/reports` returns all reports, while `GET /health/reports?ward_id=W-01` filters by ward. An unknown filter ward returns `404`.

## Action log

`GET /action-log?limit=50&offset=0` returns newest-first audit entries. `limit` is constrained to `1..200` and `offset` is non-negative.

The frontend writes actions through `POST /action-log` using the same action fields and idempotency key. Duplicate keys return the existing record.

## Heat zones

`GET /heat-zones/geojson` returns the latest stored heat-zone `FeatureCollection`.
Heat zones are stored in the PostGIS-backed `heat_zones` table and refreshed by one weekly APScheduler job. Run `alembic upgrade head` before using this endpoint.

The Earth Engine scripts require `EE_PROJECT`, `EE_LST_COLLECTION`, and `EE_LST_BAND`. The existing frontend thresholds (`27.8`, `29.4`, and `31.1` degrees Celsius) are used only when `EE_HEAT_VALUE_TYPE=wbgt`; the pipeline refuses to classify ordinary LST as WBGT.

## Weather proxy

`GET /weather/wards/{ward_id}` proxies the existing Open-Meteo hourly forecast request. Responses are cached in Redis under `weather:ward:{ward_id}` for 900 seconds. Redis errors are logged and bypassed so Open-Meteo remains available as a fallback.

## Supporting operations

The former profile, active cooling-center, and emergency-event Firestore operations use `PUT /users/{user_id}`, `GET /cooling-centers`, and `POST /emergency-events` respectively. Their tables are created by migration `002_api_support_tables`.
